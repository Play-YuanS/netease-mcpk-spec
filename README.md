# MCPK 格式逆向文档

网易《我的世界》中国版客户端私有资源包容器 **MCPK** 的二进制格式逆向研究成果。

## TL;DR

MCPK 是一个自描述的**压缩打包容器**（类似 zip，但结构完全私有），没有加密：

```
┌────────────┬──────────────────────┬─────────────────────┬──────────┐
│ 头部 64B   │ 表区 (16B×N + 13B)   │ 流区 (zlib 流序列)  │ 尾部 129B│
│ "MCPK"...  │ 文件索引+目录结构     │ 所有文件的实际数据   │ 用途未知 │
└────────────┴──────────────────────┴─────────────────────┴──────────┘
```

核心设计（也是最精妙的部分）：

1. **哈希链**：每个文件条目的 32 位名字键被拆成两半存储——高 8 位在自己身上，低 24 位存在**前一个条目**里
2. **表区前 332 条是"组区"**：以每 3 条一组的方式编码目录哈希、文件计数、段锚点
3. **流区没有目录**：想知道哪个流对应哪个文件，只能靠 zlib 逐个解压试探，配合 `contents.json`
4. 路径 → 32 位键使用一个**自定义 128 位状态哈希**（本仓库提供完整参考实现）

> **准确性声明（阅读本文前必看）**
>
> - 原始逆向过程中的结论均通过"读出 → 改写 → 游戏实测加载"闭环验证；但**本文档为事后整理，可能存在转述误差或推断错误**
> - 所有字段语义均归纳自特定版本客户端的实测样本（vanilla 560MB / vanilla_netease 1.84GB / chemistry_1.21.30），**客户端更新后格式可能改变，请勿假设长期适用**
> - 标注"未确认"的字段请勿当作事实引用；**其余内容也仅供参考，请以你自己的实测为准**

## 1. 背景

- 国际版 Bedrock 的资源包是 `.mcpack`（本质是 zip），公开格式
- 网易中国版客户端把资源包编译为**无扩展名的单文件容器**，位于游戏目录 `data/resource_packs/` 下（如 `vanilla`、`vanilla_netease`、`chemistry_1.21.30`）
- 文件本身没有任何密码学保护——难点纯在于结构未公开。本文档即该结构的完整描述

## 2. 总体布局

| 区域 | 位置 | 内容 |
|---|---|---|
| 头部 | `0x00 - 0x3F`（64 字节） | 魔数、常量、流区偏移 |
| 表区 | `0x40` 起，每条目 16 字节 | 前 332 条为组区，其后为文件条目，表尾附 13 字节 stray 条目 |
| 流区 | `doff`（头部 0x14 字段）起 | 连续排列的 zlib 流 |
| 尾部 | 最后 129 字节 | 用途未确认，改写时原样保留即可通过校验 |

条目数 N 的计算：`N = (doff - 0x40 - 13) / 16`（13 为表尾 stray 条目长度）。

实测样本（vanilla 主资源包，560 MB）：表条目 17484 = 组区 332 + 文件 17152，流 17153 个。

## 3. 头部（64 字节）

| 偏移 | 大小 | 实测值（vanilla） | 含义 |
|---|---|---|---|
| `0x00` | 4 | `"MCPK"` | 魔数 |
| `0x04` | 4 | `00 00 40 65` | 未确认 |
| `0x08` | 4 | `0x41DAAA0A`（LE） | 常量，多个不同包一致，疑似格式/构建标识 |
| `0x0C` | 4 | `57` | 常量，多个不同包一致，疑似版本相关 |
| `0x10` | 4 | `5373` | 未确认（实测排除：不是目录数 443、文件数、条目数） |
| `0x14` | 4 | `279821` | **`doff`：流区起始的绝对偏移**（本格式最重要的单一字段） |
| `0x18` | 10 | `"minecraft\0"` | 固定 ASCII 字符串 |
| `0x22` | 30 | 多为零 | 未确认 |

## 4. 流区

- 每个文件的内容是一个独立 **zlib 流**（头字节 `78 9C` / `78 DA` / `78 01`），按物理顺序紧密排列
- **没有全局流表**：解析方法是顺序扫描——遇到 `78 xx` 就用 `zlib.decompressobj` 试探解压，直到 `eof` 得到本流长度 `(comp, dec)`，然后继续下一个
- 条目与流的对应关系：条目的 `off` 字段是**相对 doff 的偏移**，且 `off`/`comp`/`dec` 三元组与扫描得到的流参数精确匹配（这也是区分"文件条目"和"组区条目"的判据）
- vanilla 层的流物理顺序：`contents.json` 位于第 4 个流（index 3），其前 3 个流对应 `contents.json` 里前 3 个路径，其后按 contents 顺序排列
- 流区结束后有 129 字节尾部块，**内容未知但必须原样保留**

## 5. 表区条目（vanilla 层，16 字节）

| 字节 | 名称 | 含义 |
|---|---|---|
| `b+0` | `X` | 名字键高 8 位 = `f1(文件名) >> 24` |
| `b+1..b+4` | `off` | u32 LE，流相对偏移 |
| `b+5..b+7` | `comp` | u24 LE，压缩后大小 |
| `b+8` | `Y` | 文件区条目：未确认；组区条目：参与锚点编码 |
| `b+9..b+11` | `dec` | u24 LE，解压后大小 |
| `b+12` | `Z` | 未确认 |
| `b+13..b+15` | `W` | u24，**下一个条目**的名字键低 24 位 |

### 5.1 哈希链（本格式最关键的设计）

条目 j 的 32 位名字键**不完整存储在条目 j 内**：

```text
key(j) = (entry[j].X << 24) | entry[j-1].W
```

- 键值 = `f1(文件名)`（仅 basename，不含目录；见第 8 节）
- 也就是说：改动任何条目，都会影响**后一个条目**的键解析
- 新增/移动条目时必须同步改写前一条目的 `W`，否则整条链失效
- 游戏按此链做完整性校验（实测：链断裂时出现模型消失、贴图紫黑、物品不可见等症状）

### 5.2 文件条目的排列规则

- 同一目录的文件条目在表内**连续成段**（段即"目录段"）
- 段内按 `f1(文件名) ^ 0x80000000` **升序**排列（符号位翻转后即可直接二分查找）
- 段与段之间的顺序由组区描述

### 5.3 stray 条目（表尾 13 字节）

表区末尾附一个不完整的条目（省略 W 字段）：

```text
stray = X(1) + off(u32) + comp(u24) + Y(1) + dec(u24) + Z(1)   = 13 字节
```

它指向一个**不在 contents.json 里声明的隐藏流**（实测样本中是一个实体材质贴图）。改写流区布局时必须同步平移它的 `off`。

## 6. 组区（表区前 332 条）

文件条目之前有 `GZONE = 332` 条结构条目，按 3 条一组组织（`GROUPS = 110` 组，330 + 2 条附加）。

### 6.1 count 4 族（每组 3 条：g0=3k, g1=3k+1, g2=3k+2）

每组围绕一个目录编码了 4 个文件计数槽位：

| 槽位 | 语义 |
|---|---|---| `g1.off`（u32） | `f1(目录名)` —— 本组对应的目录 |
| `g1.dec`（u24） | 本目录文件数 |
| `g2.comp`（u24） | 下一个目录的文件数（下一目录键 = `(g2.X << 24) \| g1.W`） |
| `g0.W`（u24） | 上一个目录的文件数 |
| `g0.off`（u24） | 上上一个目录的文件数 |

**增删文件后必须全量重算受影响目录的全部 4 族槽位**，漏一处即校验失败。

### 6.2 锚点体系（442 个槽位）

分布：每组 4 槽 `{(3k,9), (3k+1,5), (3k+2,1), (3k+2,13)}`（条目号, 条目内字节偏移），共 440 槽，外加 `{(330,9), (331,5)}` 两槽，合计 442。

每个锚点槽是一个 u24，值为**目录段首条目索引的"GZONE 相对语义"**：

```text
anchor = (目录段首条目索引 − GZONE) × 16
```

即"以组区末端为原点、以字节计的偏移"。**任何条目增删都会平移后续目录段**，全部受影响锚点必须按新段首重写。

> 踩坑警示：计算锚点平移量时必须按"文件数"而非"字节数"计数——两种算法的差异会以每条目 16 字节的粒度累积，导致后续所有锚点错位（症状：贴图/粒子/UI 渲染失败）。

## 7. contents.json

流区中的 `contents.json` 是文件清单，**必须逐字节保持官方格式**（实测改用紧凑 JSON 会加载异常）：

```text
{\r\n
    "content": [\r\n
        {\r\n
            "path": "textures/xxx.png"\r\n
        },\r\n
        ...\r\n
    ]\r\n
}\r\n
```

- 缩进：`content` 数组 4 空格、对象 8 空格、`path` 值 12 空格；换行一律 CRLF；无尾随逗号
- 路径列表按 **DFS 序**排列，排序键：

```python
def kcomp(s):  return s.lower().replace('_', '\xff')
def walk_key(path):
    parts = path.split('/')
    return [(1, kcomp(p)) for p in parts[:-1]] + [(0, kcomp(parts[-1]))]
```

即：同级中目录(1)排在文件(0)之后；比较前小写化、下划线视作大于所有常规字符。新增路径后需重新排序整个列表。

## 8. 路径哈希 f1 / f2

表区的名字键、组区的目录键都来自一个**自定义 32 位输出哈希**，从客户端二进制逆向得到（Frida hook 采样 + 算法复刻，全量样本 0 失配）：

- 128 位内部状态（h1/h2/h3，h4 恒为 0），按 4 字节小端分词轮转混合
- 双轮结构 `dbl_round`：掩码/置位 + 64 位乘法 + 两种折叠（`fold_hi`/`fold_lo`）
- 末尾短字（不足 4 字节）补零后仍做一轮；终结化两轮后异或输出
- `f1`（零终止字符串版）与 `f2`（显式长度版）逻辑相同

完整可运行的参考实现见 [hash_reference.py](hash_reference.py)，含全部常量。验证方法：对任意路径计算 `f1(basename)`，与表中 `(X<<24)|prevW` 比对。

## 9. netease 层变体

游戏同时存在两个 MCPK 大包（`vanilla` 与 `vanilla_netease`），**条目布局不同**：

| 项 | vanilla 层 | netease 层 |
|---|---|---|
| 条目键 | `(X<<24)\|前条W` 哈希链 | `b+1..b+4` 直接存 `f1(文件名)` u32 |
| 流偏移 | `off` @ b+1..b+4 | `rel` @ b+5..b+8（u32，3+1 拆放） |
| comp/dec | b+5..7 / b+9..11 | b+9..11 / b+13..15 |
| 流物理序 | 前 3 文件 + contents + 其余 | `contents.json` 是**流[0]**，流 i+1 ↔ paths[i] 一一对应 |
| 表规模 | 17484 条（17152 文件） | 67371 条（67046 文件） |
| 结构复杂度 | 高（组区/锚点/链） | 低（键值直查） |

netease 层的**内容替换**因此极其简单：定位条目（键匹配）→ 压缩新内容 → 追加新流到尾部（129 字节 trailer 前）→ 更新该条目 `rel/comp/dec` 三个字段，表区其余一字节不动。

## 10. 修改方法论（vanilla 层六阶段流水线）

对 vanilla 层做"新增文件"级别的修改，实测可靠的最小流程：

1. **段内插入**：新文件按 `f1(文件名)^0x80000000` 的二分位置插入同目录段（注意：**不支持创建新目录**——那需要在组区插 B 树节点，尚未逆向）；逐条改写受影响的 `W` 链；stray 条目 `off` 平移
2. **count 4 族全量重算**：受影响目录的本/前/后/后后计数槽
3. **contents.json 官方格式重写**：新路径并入后重新 DFS 排序
4. **全流区重排**：物理流序重排为与 contents 序一致（前 3 文件 + contents + 其余）
5. **锚点全量重写**：442 槽按新段首重算
6. **头部 doff 更新** + trailer 原样拼接

**内容替换**（不改条目数）则简单得多：替换流内容 → 更新该条目 `comp/dec`，其余不动。

### 自洽审计（无官方参考时的验证清单）

- 全流扫描数 = 原流数 + 新增数；每条文件条目的 `(off, comp, dec)` 与实际流参数三元组精确匹配
- 哈希链全表复验：`key(j) == f1(文件名)`
- 段内二分复验：按 `key^0x80000000` 对每个目录段做二分，全部命中自身
- 未替换的流与原包**逐字节一致**
- contents.json 与官方格式逐字节一致（含 CRLF/缩进）
- 组区 4 族计数与实际目录文件数一致；442 锚点与实际段首一致
- 最终以游戏实际加载 + 资源正常渲染为闭环

## 11. 未解之谜

- 头部 `0x04`、`0x10` 字段语义（排除了若干假设）
- 尾部 129 字节 trailer 的内容与用途（保留原样即可通过）
- stray 条目为何指向一个未在 contents 声明的流
- netease 层条目中 `b+0`、`b+12` 字节的作用
- 组区 330/331 两条附加条目的完整语义

## 12. 踩坑记录（症状 → 根因）

| 症状 | 根因 |
|---|---|
| 新增文件后部分模型错误/消失、世界加载卡死 | 条目追加到表尾而非段内插入，破坏了目录段连续性与锚点 |
| 贴图/粒子/UI 渲染失败 | 锚点平移公式按位置数而非文件数计算，产生每条目 16 字节的累积错位 |
| 物品不可见、贴图紫黑 | 只修复了部分指针（如只改 off 不改 W 链/count 族） |
| 修改不生效但游戏不报错 | netease 层同名文件优先级覆盖 vanilla 层（层叠问题，非格式问题） |
